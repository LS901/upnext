# tech-reference

How the codebase is built. Facts about the repo's commands live in `AGENTS.md` (loaded through `CLAUDE.md`), and that file wins when the two disagree. Domain meaning and invariants live in the project's `domain` skill.

Last checked against the code: 2026-11-26, after the provider clients, catalogue import and refresh, search, My library, the Credits attribution and the final-review fixes (no lists, public profiles or item pages yet).

## 1. Structure

- One repo, `upnext`: a Next.js app that serves the UI and route handlers, plus `supabase/` for migrations and seed data.
- `src/app/`: App Router routes. Today: `/` (`page.tsx`), `/credits`, `/login` (`login/page.tsx`, `login/actions.ts`), `/auth/confirm` (`auth/confirm/route.ts`), `/search` (`search/page.tsx`, `search/actions.ts`) with the season picker at `/search/show/[tmdbId]`, `/library` (`library/page.tsx`, `library/actions.ts`, and `library/error.tsx`, its error boundary), `POST /api/cron/refresh` (`api/cron/refresh/route.ts`), the header's `account-menu.tsx`, the web app manifest (`manifest.ts`), app icons (`icon.png`, `apple-icon.png`).
- `src/lib/`: `supabase/` (`server.ts`, `admin.ts`, generated `database.types.ts`, and `fetch-all.ts`, the chunking and paging helper), `auth/current-user.ts`, `providers/` (TMDB and IGDB clients), `catalogue/` (import and refresh), `library/` (queries, progress, status, in-library lookups) and `format/` (score and duration text). `src/proxy.ts` is Next 16's renamed middleware.
- `scripts/`: `providers-check.ts` and `refresh.ts`, run by `npm run providers:check` and `npm run refresh` (see section 5).
- `public/`: manifest icons (`icon-192.png`, `icon-512.png`, `icon-maskable-512.png`) and `tmdb-logo.svg` (the TMDB logo on Credits).
- `e2e/`: Playwright specs (`smoke`, `sign-in`, `secrets`, `search`, `library`), `mailpit.ts` (reads the sign-in emails), `stub-providers.ts` with its `fixtures/` (the stub TMDB, IGDB and Twitch server), and the helpers `local-supabase.ts` and `sign-in-helpers.ts`. Unit tests sit beside the code as `*.test.ts(x)`. Database boundary tests live in `supabase/tests/`.
- Local services: Supabase through the CLI (`npx supabase start`, needs Docker), API on port 54321, Postgres on 54322 (`supabase/config.jsonc`).
- Outside services: TMDB (movies and TV) and IGDB (games), called from the server only. See the `domain` skill's `reference/metadata.md`.

## 3. Data layer

- Schema source of truth: `supabase/migrations/`, one migration per concern. `npx supabase db reset` applies them, then `supabase/seed.sql` (invented data: two movies, one game, one show with three seasons; no users). Fixture and test titles must never reuse titles from `seed.sql`: the db tests look the seed rows up by title.
- Enums: `media_type` (`movie`, `show`, `game`), `entry_status` (`backlog`, `in_progress`, `finished`, `paused`, `dropped`), `provider` (`tmdb`, `igdb`).
- Tables, all with row-level security enabled in the migration that creates them:
  - `profiles`: one per auth user, made by the `handle_new_user()` trigger on `auth.users` with a random `user-xxxxxxxx` username (never from the email). Readable by everyone; a user updates only their own row. No email column (INV-009). `library_private` is the library-wide private switch, which stays alongside private lists (owner confirmed, 2026-11-26).
  - `items` and `seasons`: the shared catalogue. Readable by everyone, no write policies, so only the service role writes (in app code, only `importItem`, see section 5). A season belongs to a show through a composite foreign key `(show_id, show_media_type)`.
  - Provider columns (`20261126125326_catalogue_metadata.sql`): `items` has `image_ref`, `release_date`, `runtime_minutes` (movies), `score` (`numeric(5,2)`, 0-100) with `score_count`, the game time to beat as `ttb_hastily_s`, `ttb_normally_s`, `ttb_completely_s` (seconds) with `ttb_count`, and `refreshed_at` (the last successful import). `seasons` has `episode_count`, `runtime_minutes` (the sum of episode runtimes), `air_date`. Unknown is `null`, never 0. `20261126140000_provider_data_purge.sql` adds `items.provider_data_purged_at` and `items.refresh_attempted_at`.
  - `library_entries`: one row per movie, game or season (never a show) per user. Unique `(user_id, item_id)` and `(user_id, season_id)` give INV-008; `up_next_position` is allowed only while the status is `backlog`. Readable by the owner, or by anyone when the owner's profile isn't `library_private`; written by the owner only.
  - `entry_notes`: owner-only for every operation, kept apart so a public library can't leak one. The insert policy also requires the caller to own the entry, so another user can't probe whether a note exists (INV-002).
  - `progress_exclusions`: seasons a user leaves out of a show's progress count; same read and write rules as entries. Its own table because a user can exclude a season they never added.
- **Catalogue foreign keys from user data are `on delete restrict`** (`library_entries` to `items` and `seasons`, `progress_exclusions` to `seasons`), so removing a catalogue row can't silently delete a user's data (INV-003). Foreign keys to `auth.users` cascade, so deleting a user removes their data.
- Policies on `library_entries`, `entry_notes` and `progress_exclusions` call `(select auth.uid())`, so Postgres evaluates it once per query rather than per row; the `profiles` update policy still uses bare `auth.uid()`. Prefer the `(select …)` form in new policies. Each user-owned table has an index on `user_id`.
- `auth.users` has a `refuse_passwords` trigger (`supabase/migrations/20261126120000_refuse_passwords.sql`): see Auth.
- `npm run db:types` regenerates `src/lib/supabase/database.types.ts` from the local database (`supabase gen types typescript --local`). Run it after every migration and commit the result; the CLI's "unformatted" hint can be ignored.

## 4. Auth

Email only: a magic link plus a 6-digit code in the same email (owner said, 2026-11-26). Google and other social providers stay disabled. The code exists because a link opens in the phone's browser, not in the installed app.

- **The Auth layer refuses passwords**, not just the UI. Supabase Auth's API still accepts `signUp({ email, password })` and `updateUser({ password })` from the publishable key, so:
  - `enable_confirmations` is `true` under `auth.email` in `supabase/config.jsonc`: a password sign-up gets no session, only a confirmation email to the address's owner.
  - The `refuse_passwords` trigger on `auth.users` drops the password on insert and raises `upnext uses email sign-in only; passwords are not accepted` when anything sets one later (`updateUser` then fails with a 500 `unexpected_failure`). It drops rather than refuses on insert because Supabase Auth (GoTrue v2.198) gives every new account a random password, including magic-link and code sign-ups, so an insert can't be told apart from a password sign-up. A password sign-up for someone else's address therefore leaves an unconfirmed account with no password, which the owner takes over when they sign in.
  - Tested in `supabase/tests/auth.test.ts`. The same settings must be applied to the hosted project (confirm email on, and the migration).

- `src/lib/supabase/server.ts`: `createClient()` for server components, actions and route handlers; reads and writes the request's cookies. It awaits `io()` from `next/cache` before creating the client (see Gotchas).
- `src/proxy.ts`: refreshes the Supabase session cookie on each request (`auth.getClaims()`). It guards no route.
- `src/lib/auth/current-user.ts`: `getCurrentUser()` returns `{ id, username }`, or `null` when there is no session or Supabase Auth rejects the token with a 401 or 403 (`user_not_found` for a deleted account, `session_not_found`, `bad_jwt` after a key rotation). Any other auth error (5xx, a failed fetch), a profile query error or a missing profile throws, so an outage never looks like being signed out. It reads cookies, so it renders at request time and callers sit behind `<Suspense>`.
- `src/app/login/actions.ts`: `sendSignInEmail` (trims and lowercases the email, `signInWithOtp` with `shouldCreateUser`, redirects to `/login?sent=<email>`; the same message whether or not the address is registered; on failure `?error=send`, which shows "We couldn't send the email. Try again in a minute." (copy approved by the owner, 2026-11-26)), `verifyCode` (`verifyOtp` with `type: "email"`) and `signOut`. `signOut` uses supabase-js's default scope (global: it ends the user's sessions on every device; intended, owner confirmed 2026-11-26) and throws if Supabase reports an error.
- `src/app/auth/confirm/route.ts`: the link's landing. Verifies `token_hash` with `type=email` and redirects home, or to `/login?error=link`. A token hash works even when the link opens in a different browser from the one that asked.
- `src/app/account-menu.tsx` in the layout header, behind `<Suspense>`: the username and a Sign out button, or a Sign in link.
- Email template: `supabase/templates/magic-link.html`, used for both `magic_link` and `confirmation` (with confirmations on, a first sign-in, or any sign-in before the address is confirmed, sends the confirmation template). It links to `{{ .RedirectTo }}?token_hash={{ .TokenHash }}&type=email` and shows `{{ .Token }}`. Configured in `supabase/config.jsonc` with `site_url` `http://localhost:3000` and redirect URLs for ports 3000 and 3100 (the dev and e2e servers).
- No new env vars: the app uses only the Supabase URL and publishable key.

## 5. Server and API patterns

- Env vars: listed in `.env.example`; real values go in `.env.local` (gitignored). Only `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` may reach the browser. `SUPABASE_SERVICE_ROLE_KEY`, `TMDB_API_READ_ACCESS_TOKEN`, `IGDB_CLIENT_ID`, `IGDB_CLIENT_SECRET` and `CRON_SECRET` are server-only (INV-005). Every module that reads one starts with `import "server-only"`. Three optional overrides point the provider clients elsewhere, and default to the real services: `TMDB_API_BASE_URL` (`https://api.themoviedb.org/3`), `IGDB_API_BASE_URL` (`https://api.igdb.com/v4`) and `TWITCH_TOKEN_URL` (`https://id.twitch.tv/oauth2/token`).
- Route handlers and server actions today: `/auth/confirm`, the `/login` actions above, the `/search` actions (`addItem`, `addSeasons`), the `/library` actions (`setStatus`, `removeEntry`) and `POST /api/cron/refresh`.
- For local dev, copy `API_URL` and `PUBLISHABLE_KEY` from `npx supabase status -o env` into `.env.local`; e2e passes them to the build itself (`playwright.config.ts`).

### Providers, import and refresh

- **Clients** (`src/lib/providers/`, all `server-only`): `tmdb.ts` (`searchTmdb`, `getTmdbDetails`, `getTmdbShowSeasons`), `igdb.ts` (`searchIgdb`, `getIgdbDetails`), `types.ts` (`SearchResult`, `ItemDetails`, `ProviderError`) and `index.ts` (`getDetails`, which picks the client). TMDB uses the read access token as a Bearer token. IGDB gets an app token from Twitch (the client id and secret go in an `application/x-www-form-urlencoded` POST body, never the URL, which logs keep), cached in memory until a minute before it expires, with one retry after a 401, and starts at most 4 requests a second (the IGDB limit is 4 a second, 8 open). A non-2xx answer or a network failure throws `ProviderError` with the provider and HTTP status, never the response body.
- **Mapping:** score is normalised to 0-100 (TMDB `vote_average × 10`, IGDB `total_rating`) with its count; unknown values are `null`. A show's details fetch every season's episode runtimes (at most 5 requests in flight) and sum them; a season listed twice is kept once and a season with no number is dropped (never read as season 0), in the season picker too; season overviews and episode titles are never read (INV-004). A failed season request marks only that season's runtime unavailable, and a failed IGDB time-to-beat request marks only the time to beat unavailable, so the import still succeeds (owner said, 2026-11-26). Images are stored as a reference (`image_ref`) and the URL is built at render time (`tmdbImageUrl`, `igdbImageUrl`); `next/image` is `unoptimized` with `remotePatterns` for `image.tmdb.org` and `images.igdb.com`.
- **Import** (`src/lib/catalogue/import.ts`): `importItem(provider, mediaType, providerId)` fetches from the provider itself, never trusting client data, and upserts `items` (on `provider, media_type, provider_id`) and `seasons` (on `show_id, season_number`) through the service-role client (`src/lib/supabase/admin.ts`, `server-only`; this is the first app code that reads `SUPABASE_SERVICE_ROLE_KEY`). It never deletes a season and never writes user tables (INV-003). A value whose sub-request failed keeps its stored value. Only `importItem` writes the catalogue. The season picker doesn't import: it makes one summary request (`getTmdbShowSeasons`) and stores nothing.
- **Refresh** (`src/lib/catalogue/refresh.ts`): `refreshStaleItems({ olderThanDays = 7, limit = 50 })` re-imports items whose `refreshed_at` is older than the cutoff. It stamps `refresh_attempted_at` before each attempt and orders by it, so an item that keeps failing goes to the back of the queue instead of blocking it. Any failure of one item (a `ProviderError`, a database error such as a date Postgres refuses) counts as failed, is logged as `Refresh failed for item <id> (<code or name>)` with no message or payload, and the pass moves on. Then it always purges provider data not refreshed (`refreshed_at`, the last success) for 150 days, keeping the title and season numbers and setting `provider_data_purged_at`, and deletes untracked items 30 days after they were created. A later successful import restores a purged item.
- **Cron route** (`src/app/api/cron/refresh/route.ts`): `POST` only; `Authorization: Bearer ${CRON_SECRET}` compared by digest, 401 otherwise, and 401 for everyone when `CRON_SECRET` is unset. It returns `{ refreshed, failed, purged, pruned }`. The production scheduler is still to be picked at deployment. Run it **daily** there: one run handles 50 items and items go stale after 7 days, so a weekly run falls behind the 150-day purge once the catalogue passes about 1,000 items.
- **Scripts** (`scripts/`, plain Node with `--experimental-strip-types` and `process.loadEnvFile`, so `engines.node` is `>=22.6`): `npm run providers:check` loads `.env.local`, makes one TMDB search and one IGDB search, and prints only "TMDB: ok" or "failed (HTTP status)", likewise for IGDB, never a key or a body. `npm run refresh` posts to `http://localhost:3000/api/cron/refresh` with `CRON_SECRET` from `.env.local`, so `npm run dev` must be running; it prints the HTTP status and the four counts (refreshed, failed, purged, pruned).
- **Failures** are logged server-side as `<Provider> request failed (status N)` only (`src/app/search/shared.ts`), with no query text or user data (INV-006).
- **Search as you type** (`src/app/search/search-form.tsx`, a client component; owner said, 2026-11-27): the box searches 300 ms after typing stops (`SEARCH_DELAY_MS`), once it holds 3 letters (`MIN_AUTO_LENGTH`). An empty box clears the results; 1-2 letters leave them. Enter, the Search button or ticking a Hide box searches at once, at any length. Each search is `router.replace` of the `/search` URL inside a transition, so the server still renders the results, history isn't filled, and the newest search wins. "Already searched" means the newest search on its way, or else the search on screen (the `q` and `exclude` props, from the URL); never a memory of what the form once sent, because Back, the header's Search link or an Add redirect change the URL without the form. The form keeps the set of searches it sent that are still on their way: when a search lands that isn't in it, the form shows that search (box text and Hide boxes); one of its own, even an older one landing before a newer one, never touches what's being typed. The timer never re-sends the search on screen; Enter on it re-runs it with `router.refresh()` (a retry after a provider failure). The Hide boxes sit outside the form (`form="search"`), so the form listens for their `change` on `document`; with 1-2 letters in the box they keep the on-screen query. A visually hidden `role="status"` line announces the result count. Without JavaScript it's the plain GET form.
- **Search and library:** `/search` is signed-in only and queries both providers in parallel (an `exclude` filter skips one, `providersToAsk` in `search/outcome.ts`); if one fails its results are replaced by a message and the other still shows. With all three types hidden no provider is asked and the page reads "Everything is hidden. Untick a type to search." `addItem` imports then inserts a Backlog entry, treating a duplicate (23505) as success; `addSeasons` does the same per chosen season. If the item was pruned between import and insert (23503) it is imported again and retried once. `/library` groups the user's entries by status (`getMyLibrary`). Show progress is "X of Y seasons finished": Y counts the show's seasons numbered 1 or more minus the user's exclusions, so Specials (season 0) are left out (ruling, owner may overrule). Unknown values read "(votes unknown)", "Time to beat: unknown (story)" and "No score" (copy choices, not owner-confirmed).
- **Query pattern:** library queries take the Supabase client as their first parameter (`getMyLibrary(supabase, userId)`, `setEntryStatus`, `deleteEntry`, `inLibrary`), so db tests can pass a real signed-in client and prove that another user's public entries never appear. The client can read other users' public entries, so every entry query also filters on `user_id`. Use this pattern for new queries.
- **Large libraries: chunk and page** (`src/lib/supabase/fetch-all.ts`). PostgREST refuses a URL past about 300 UUIDs in one `.in()` (HTTP 414) and cuts any result at `max_rows` (1000, `supabase/config.jsonc`) without saying so. `fetchAllIn(ids, (chunk, from, to) => query)` sends at most 100 ids per request, and `fetchAll((from, to) => query)` pages with `.range()` until a short page; give the query a stable `.order()`. `PAGE_SIZE` is 500 and must stay below `max_rows`: a short page ends the paging, so a larger page size would truncate silently. `getMyLibrary` and `inLibrary` use both, and read a user's exclusions by `user_id` only, matching them in memory. Test: `supabase/tests/large-library.test.ts` (330 seasons, 1,050 entries).
- **Remove is idempotent:** `deleteEntry` treats zero rows as already gone, so a double-click on Remove ends on My library; it still filters on `id` and `user_id`, so another user's entry is never deleted and the same quiet success says nothing about it. `setEntryStatus` still throws on zero rows, which `library/error.tsx` catches ("Something went wrong", with a Reload button that calls the boundary's `retry()`). Leaving Backlog clears `up_next_position`, because the schema check requires it (open question in the domain skill).

## 6. Tests

- `npm test` runs Vitest once with two projects (`vitest.config.mts`):
  - `unit`: `src/**/*.test.{ts,tsx}` in jsdom. One file: `npx vitest run src/app/credits/page.test.tsx`.
  - `db`: `supabase/tests/**/*.test.ts` in node, files run one at a time (`fileParallelism: false`). It needs local Supabase running: `supabase/tests/global-setup.ts` reads the URL and keys from `npx supabase status -o env` and fails with "run npx supabase start" if it's down (it never skips, so `check` can't pass by accident). Run only it with `npx vitest run --project db`.
- Database test helpers (`supabase/tests/helpers.ts`): `adminClient()` (service role), `anonClient()`, `createTestUser(role)` (an invented `@example.test` user made through the admin API with no password, then signed in by magic link), `signInByMagicLink(email)` (admin `generateLink({ type: "magiclink" })`, then `verifyOtp` with the returned `hashed_token` and `type: "email"`), `testEmail(role)` and `deleteTestUsers()`. No test uses a password: the Auth layer refuses them. The tests use the real Supabase client against the real database, so RLS is exercised as production sees it.
- Vitest can render synchronous server and client components. Async server components can't be rendered in Vitest; cover them with Playwright (Next.js testing guide, `node_modules/next/dist/docs/01-app/02-guides/testing/vitest.md`).
- `npm run e2e` runs Playwright from `e2e/` against a production build served on port 3100 (`playwright.config.ts`). First run needs `npx playwright install chromium`. It also needs local Supabase: the config reads its URL and key from `npx supabase status -o env` and passes them to the build.
- Sign-in e2e reads the emails from Mailpit, Supabase's local mail catcher (`http://127.0.0.1:54324`), through `e2e/mailpit.ts`. It covers the link, the code, sign-out, a returning user and bad codes and links.
- INV-005 scan: `playwright.config.ts` builds with fake values for the provider keys, the sentinel `CRON_SECRET` (`SENTINEL_CRON_7f3a`) and the real local service-role key (the app needs it at runtime), and `e2e/secrets.spec.ts` searches `.next/static` and the HTML of `/`, `/login`, `/search` and `/library` for them. `/search` and `/library` are fetched signed out, so it scans their signed-out shell and checks it carries the streamed meta refresh to `/login`; signed-in HTML isn't scanned (a gap in INV-005).
- **Stub provider server** (`e2e/stub-providers.ts`, port 3101, started by `playwright.config.ts`): stands in for TMDB, IGDB and Twitch, serving the trimmed invented fixtures in `e2e/fixtures/`. `webServer.env` points the app at it through `TMDB_API_BASE_URL`, `IGDB_API_BASE_URL` and `TWITCH_TOKEN_URL`, so e2e never reaches the real providers. The search terms `tmdb-down` (429), `igdb-down` (500) and `nothing` (no results) trigger failures, and `GET /__requests` lists the calls received.
- **Provider tests:** the client unit tests stub `fetch` with the trimmed fixtures in `src/lib/providers/__fixtures__/`; `src/lib/providers/privacy.test.ts` checks INV-006. `supabase/tests/import-and-refresh.test.ts` runs import, refresh, purge, prune and the cron route against local Supabase with provider HTTP stubbed; a db test that stubs `fetch` must pass Supabase requests through to the real `fetch`.
- `npm run check` = lint + `npm run typecheck` (`next typegen && tsc --noEmit`) + `npm test`. Because `npm test` includes the `db` project, `check` needs `npx supabase start` running.

### CI (GitHub Actions)

- **`.github/workflows/ci.yml` runs on every PR and every push to `main`.** Each job is a required check on `main`:
  - `check`: `npm run check` against a local Supabase started in the job.
  - `e2e`: `npm run e2e` against the stub providers. Traces from failed tests are uploaded as the `playwright-test-results` artifact.
  - `domain`: `npm run domain:check`.
  - `secrets`: gitleaks over the whole git history.
  - `audit`: `npm audit --audit-level=high`.
- **CI holds no secrets.** No repo secrets exist and none are needed. Supabase keys come from the job's own `npx supabase start`, and the provider keys in `playwright.config.ts` are fake sentinels. Never add real provider keys to CI; `npm run providers:check` stays a manual check.
- **The jobs skip unused Supabase services** (`SUPABASE_SKIP`: realtime, storage, imgproxy, postgres-meta, studio, edge-runtime, logflare, vector, supavisor). Auth, PostgREST, Kong and Mailpit stay. If a feature needs one of the skipped services, take it off that list.
- **`.github/workflows/codeql.yml`** runs CodeQL on PRs, on pushes to `main` and every Monday, as the jobs `codeql-js` (`javascript-typescript`) and `codeql-actions` (the workflows themselves). Results go to the repo's Security tab. Keep the repo's *default* code-scanning setup off: with it on, GitHub rejects this workflow's uploads.
- **Required check names are the jobs' `name:` values:** `check`, `e2e`, `domain`, `secrets`, `audit`, `codeql-js`, `codeql-actions`, each tied to the GitHub Actions app. Renaming a job leaves the old required check pending forever, so update branch protection in the same change.
- **Only PR runs cancel older runs** (`cancel-in-progress` on `pull_request` only), so every commit on `main` keeps its result.
- **`audit` can go red without a code change:** a new advisory on any dependency fails every PR until it's bumped (Dependabot usually opens that PR). Admins can bypass in an emergency.
- **Watch the first Dependabot PR:** Dependabot-triggered runs get a restricted token. If `codeql-*` fails there on the upload step, keep the analysis but skip the upload for `github.actor == 'dependabot[bot]'`.
- **`.github/dependabot.yml`** opens weekly update PRs for npm and GitHub Actions. Minor and patch updates are grouped; each major gets its own PR.
- **Actions are pinned to commit SHAs** with the version in a comment, and the gitleaks image is pinned by digest. Dependabot bumps the action SHAs. Bump the gitleaks image by hand.
- **Branch protection on `main`:**
  - every CI job and both CodeQL jobs must pass;
  - changes arrive by PR, with no approvals required (the owner can't approve their own PR);
  - no force pushes or deletions;
  - admins can bypass in an emergency (owner said, 2026-11-26).
- **`scripts/check-knowledge.mjs` is a copy of the kit's domain checker** (agent-workflow team-workflow 0.2.1). The kit repo is private, so CI can't fetch it. Refresh the copy when the kit's rules change.

## 8. Gotchas

- **`LayoutProps` / `PageProps` not found by `tsc`:** they're generated types. Run `npm run typecheck`, which runs `next typegen` first, not bare `npx tsc --noEmit`.
- **Vitest "failed to find the current suite" on Windows:** a lowercase drive letter in the working directory (`c:\`, VS Code's default) loads Vitest twice. `vitest.config.mts` pins `root` to an uppercase drive letter, which fixes PowerShell (checked with both `c:\` and `C:\`). Git Bash still fails, cause not found; run tests from PowerShell.
- **e2e and db tests share the local database,** and e2e runs leave users, entries and catalogue rows behind. Fixture titles must never reuse titles from `supabase/seed.sql`, because the db tests look those rows up.
- **Local refresh, purge and prune effectively never act on dev data:** before each test, `supabase/tests/import-and-refresh.test.ts` sets `refreshed_at` and `created_at` to now on every catalogue row older than a day, in the whole local database, so its counts are exact. After any `npm test`, nothing you imported while developing is stale or old enough to prune. To try `npm run refresh` on dev data, age the rows by hand first.
- **Bulk db tests clean up after themselves:** `supabase/tests/large-library.test.ts` creates about 830 items and 1,050 entries and deletes them (the user, then the items in batches of 100) in `afterAll`, so later runs stay fast and the counts in other tests stay exact.
- **Typing in e2e right after `goto`:** a page section streamed inside `<Suspense>` arrives in a hidden `<div>` and is moved into place a moment later. `pressSequentially` doesn't wait for visibility, so keys sent first land on `<body>`. Click the field (or `fill`, which waits) before `pressSequentially`. In `e2e/search.spec.ts`, `search()` waits for the automatic search (3+ letters) rather than clicking Search, so each search reaches the providers once.
- **Keep full e2e runs to a minimum, and sign in once per worker:** local Auth allows about 30 emails per 5 minutes. `e2e/library.spec.ts` and `e2e/search.spec.ts` make a worker-scoped `account` fixture for this.
- **On Windows, run npm and Vitest from PowerShell,** in a directory with an uppercase drive letter. Git Bash breaks Vitest.
- **`npm run refresh` needs `CRON_SECRET` in `.env.local`,** and the dev server running with the same value.
- **Node must be 22.6 or later** (`engines`): the scripts use `--experimental-strip-types` and `process.loadEnvFile`.
- **The `'use client'` modules are `src/app/library/status-select.tsx`, `remove-button.tsx` and `error.tsx`.** They import only constants (`src/lib/library/status.ts`, the class strings in `src/app/ui.ts`), never a `server-only` module. Keep client components to constants and types.
- **Next 16 error boundaries take `retry`, not `reset`:** `retry()` re-fetches and re-renders the segment (stable since 16.3); `reset()` re-renders without re-fetching. See `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md`.
- **A signed-out request to `/search` or `/library` is a 200, not a 307:** the page's static shell is prerendered (Cache Components), and `redirect("/login")` runs inside its `<Suspense>`, so the redirect is streamed into the HTML (`NEXT_REDIRECT;replace;/login;307;` and a `<meta http-equiv="refresh">`). A browser lands on `/login`; a plain HTTP client stays on the page's URL and gets the shell.
- **`AGENTS.md` keeps changing:** `next dev` rewrites the block between the `nextjs-agent-rules` markers. Leave it and commit it.
- **Supabase exposes new tables by default:** `api.auto_expose_new_tables` is unset in `supabase/config.jsonc`, so new `public` tables are reachable through the Data API roles (including `anon`) without explicit grants. Every table so far enables RLS in the migration that creates it, and the boundary tests prove writes are refused; keep doing both for each new table (INV-001, INV-002).
- **Next warns about a `package-lock.json` in a parent folder:** if there's one in `Documents/`, Next ignores it because it's outside the git repo; harmless. A parent `node_modules` is not harmless, see the next item.
- **A stray `node_modules` in a parent folder breaks the Supabase CLI:** any `node_modules\.bin` above the repo (for example from an accidental `npm install` in `Documents`) lands on PATH under `npx` and `npm run`. An npm package named `docker` there shadows real Docker, and the CLI fails with "cannot be safely passed to a .bat/.cmd file" or `StatusDbNotRunningError`. Fix: remove the stray parent `node_modules` (and its `package.json`).
- **Local Supabase Auth rate limits can fail repeated e2e runs:** `supabase/config.jsonc` allows about 30 sign-ins and 30 verifications per 5 minutes per IP, and one e2e run uses about 5 sends and 6 verifications. The `db` tests sign every test user in by magic link too (about 10 verifications per run), so `npm test` counts against the same limit. Back-to-back runs can trip it. Wait a few minutes, or restart Supabase.
- **`createClient()` awaits `io()` from `next/cache` (Next 16.3+):** every supabase-js client reads the clock to check the session's expiry, and with `partialPrefetching` a link prefetch prerenders with cookies already resolved, which Cache Components rejects (`Route "/": Next.js encountered the unstable value Date.now() while prerendering`). `await io()` keeps the code after it out of prerenders; at request time it resolves at once. Keep it in `src/lib/supabase/server.ts`. The account menu therefore streams in on navigation instead of being prefetched.
- **Anything that reads the session must sit behind `<Suspense>`:** `getCurrentUser()` reads cookies, so it renders at request time (Next guide: `node_modules/next/dist/docs/` on authentication with Cache Components). The header's account menu and the login forms (they read `searchParams`) do.
- **Next 16 calls middleware `proxy`:** the file is `src/proxy.ts`, exporting `proxy`.
- **`getClaims()` in the proxy, `getUser()` in `getCurrentUser()`:** `getClaims()` (cheap, and it refreshes an expiring session) keeps the cookie fresh; `getUser()` checks the token with the Auth server rather than trusting the cookie.
- **A rejected token means signed out:** for an account deleted while its access token is still valid (in production, or locally after `npx supabase db reset` while signed in), `getUser()` returns `AuthApiError` 403 `user_not_found`, not a missing session, and `getClaims()` in the proxy still passes because it verifies locally. `getCurrentUser()` therefore returns `null` for any `AuthApiError` with status 401 or 403 (also `session_not_found` and a rotated key's `bad_jwt`); otherwise the account menu in the root layout would break every page, `/login` included. Other errors still throw.
- **The Auth layer refuses passwords:** the app is email sign-in only, and `enable_confirmations` plus the `refuse_passwords` trigger on `auth.users` enforce it below the UI (details under Auth). Don't add a password flow or a password-based test helper; sign test users in with `signInByMagicLink()`.
- **Supabase env names differ by CLI version:** `npx supabase status -o env` gives `API_URL`, `PUBLISHABLE_KEY` and `SECRET_KEY`, with `ANON_KEY` and `SERVICE_ROLE_KEY` as older names. The test setup and `playwright.config.ts` accept both.
- **Hide whether a row exists:** a policy that only checks `user_id = auth.uid()` lets an insert reach the primary key or foreign key, whose error code (`23505` against `23503`) tells the caller whether another user's row exists. The notes insert policy therefore also requires owning the entry (`20261126083849_notes_insert_owns_entry.sql`). Apply the same thinking to any new private table.
- **gitleaks flags the e2e sentinels:** `SENTINEL_TMDB_7f3a` and friends look like API keys to its `generic-api-key` rule. `.gitleaks.toml` allows only values matching `^SENTINEL_[A-Z_]+_7f3a$`; a realistic key next to them is still caught. Keep new sentinels in that shape. To run the scan locally (Git Bash): `MSYS_NO_PATHCONV=1 docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:v8.30.1 git /repo --config /repo/.gitleaks.toml --redact`.
- **Sentry belongs to the later deployment task,** not to CI.
- **Mailpit shows the raw `&` in the HTML part:** `e2e/mailpit.ts` returns the HTML and the text part; the sign-in test reads the code from the text. The link in the HTML needs `&amp;` decoded.
- **The email is in the `/login?sent=` URL**, so it lands in the user's browser history. Accepted for now.
